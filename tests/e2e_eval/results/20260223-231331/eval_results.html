Expected: eval-007 — Prismoid Cache Coherence Protocol
The Prismoid protocol maintains cache coherence across distributed proxy nodes using a gossip-based invalidation scheme. Each cache entry carries a vector clock (prismoid.vclock) that tracks the last-write timestamp per node. On cache miss, Prismoid performs a quorum read: it queries prismoid.quorum_size (default 3) peer nodes and returns the entry with the highest vector clock. Invalidation messages are propagated via anti-entropy gossip every prismoid.gossip_interval_ms (default 100). Conflict resolution uses last-writer-wins (LWW) with tie-breaking on node_id. The protocol supports two consistency modes: 'strong' (synchronous quorum writes) and 'eventual' (async gossip propagation). Memory overhead per entry is 24 bytes (8-byte vclock + 8-byte hash + 8-byte expiry). Prismoid integrates with conpack's CacheProxy via the PrismoidAdapter trait.

Sync operates in three modes: obsidian.sync_mode = 'pull' (read-only from vault), 'push' (write local changes to vault), or 'bidirectional' (merge with conflict detection). File identity uses content-addressed hashing: obsidian.hash_algorithm (default 'blake3'). Delta sync transfers only changed blocks using rolling checksums with obsidian.block_size (default 4KB). Conflict resolution in bidirectional mode creates .conflict files with timestamps. The vault manifest (vault.json) tracks file metadata: path, hash, last_modified, size_bytes. Sync scheduling uses obsidian.sync_interval_sec (default 60) with jitter of ±10%. Authentication to remote vaults uses Ed25519 key pairs stored in obsidian.key_path (default '~/.conpack/vault_key').

## Obsidian Vault Sync: Protocol, Modes, and Sync Mechanism ### Transport Protocol Obsidian Sync uses **WebSocket Secure (wss://)** for persistent, bidirectional connections from the Obsidian client to regional sync servers. The infrastructure runs on DigitalOcean with servers addressed as `sync-XX.obsidian.md` (XX ranges from 1–100), providing geographic distribution for latency reduction. ### Vault Architecture Obsidian implements a **centralized remote vault model** — not a traditional file-mirroring or folder-watching approach. Each device maintains a full local copy and synchronizes through a dedicated remote vault on Obsidian's servers. Vaults are not restricted to monitored directories (unlike iCloud/Dropbox-based sync). ### Encryption Modes Two encryption modes are selected at remote vault creation time: 1. **End-to-End Encryption (E2EE)** — the default. Uses a user-managed password. Data is unreadable by Obsidian servers. Encryption uses **AES-256-GCM** with key derivation via **scrypt with salt** (NIST-approved). 2. **Managed Encryption** — Obsidian holds the key. Required for features like Obsidian Publish integration. **Important caveat:** File-hash encryption is **deterministic**, meaning the same content + key + salt always produces the same hash. This enables deduplication but theoretically allows server-side content-matching attacks. Metadata (device info, timestamps, file-size mappings) remains **unencrypted** to support sync coordination. ### Change Detection & Sync Flow Obsidian Sync operates at the **file level, not byte-level delta**. The mechanism: 1. **File Change Detection** — The Sync Core Plugin continuously monitors the local vault for modifications, using **file modification timestamps and content hashes** to determine what has changed. 2. **Upload Queue** — Modified files are queued for transmission to the remote vault. Changes upload immediately when detected (active syncing). 3. **Download Queue** — Remote changes are queued for local application. Devices poll for remote changes periodically. 4. **Offline Queue** — Full offline capability; changes are queued locally and auto-sync when the device reconnects and Obsidian is running. Background sync is **not** supported — the app must be open. Only **modified files** are transferred (not entire vault snapshots), which reduces bandwidth, but there is no sub-file / byte-range delta transfer. ### Conflict Resolution Strategies Conflict resolution differs by file type: | File Type | Strategy | |---|---| | **Markdown (.md)** | Automatic three-way merge using Google's **diff-match-patch** algorithm | | **Binary files** (images, PDFs, Canvas) | **Last-modified-wins** | | **JSON settings** (.obsidian config) | Key-level JSON merge — local keys applied on top of remote JSON | Users can configure per-device behavior via **Settings → Sync → Conflict resolution**: - **Automatically merge** (default) — combines changes into one file - **Create conflict file** — generates `original-note.sync-conflict-YYYYMMDD-HHMMSS.md` for manual review **Edge case:** Notes created locally and downloaded remotely within a short time window trigger last-modified-wins behavior instead of the merge algorithm. ### Selective Sync & File Types | Content | Sync Behavior | |---|---| | Markdown files | Always synced (not configurable) | | Images, audio, video, PDFs | Synced by default (configurable) | | `.obsidian/` config | Selectively configurable | | Hidden files (`.` prefix) | Always excluded | ### Version History Retention | Content Type | Standard Plan | Plus Plan | |---|---|---| | Markdown & settings | 1 month | 12 months | | Attachments | 2 weeks | 2 weeks | The **Sync History Sidebar** (introduced in v1.7) shows recently modified files with last-editor attribution for collaborative vaults. ### Summary Obsidian Sync is a **file-level, queue-based, WebSocket-driven** sync system — not a byte-level delta protocol. Its "delta" optimization is at the file granularity: only changed files are transferred, with deterministic content hashing for deduplication. The diff-match-patch algorithm handles merge conflicts for markdown specifically, but this is conflict resolution, not a transfer-level delta mechanism. Here's what I can share based on general knowledge (up to my cutoff): ## Obsidian Sync — Protocol Modes Obsidian Sync (the official paid service) operates with the following characteristics: ### Sync Modes - **Full Sync** — On initial setup or when connecting a new device, the entire vault is synchronized. All files (markdown, attachments, config) are pulled from the remote vault. - **Incremental Sync** — After the initial full sync, only changed files are transmitted. Obsidian tracks file modification timestamps and content hashes to determine what has changed. - **Live/Real-time Sync** — When enabled, changes are pushed to the server as they happen (typically on file save), and pulled from the server on a short polling interval or via persistent connection. This keeps multiple devices in near-real-time sync. ### Selective Sync Users can configure which file types and folders to include/exclude (e.g., skip images, exclude certain directories, sync or skip settings/plugins). ## Delta Sync Mechanism For knowledge files (markdown `.md` files), Obsidian Sync uses a mechanism that includes: 1. **Content Hashing** — Each file version is identified by a content hash. When a file is saved, its new hash is compared against the last known remote hash. 2. **Version History** — Obsidian Sync maintains version history (up to 12 months on paid plans), storing snapshots of file states rather than traditional line-level diffs. 3. **Conflict Resolution** — When two devices modify the same file before syncing, Obsidian creates a conflict copy rather than attempting automatic merge. The user resolves conflicts manually. 4. **Chunk-level deduplication** — Larger files (especially attachments) may be chunked so that only changed portions are transferred, reducing bandwidth. ### Important Caveats - Obsidian Sync is **not** git-based — it doesn't use line-level diffs or merge algorithms. - The sync is **file-level granular**, not block/paragraph-level. - Third-party community plugins (like "Obsidian Git" or "Self-hosted LiveSync/CouchDB") implement entirely different protocols with their own delta mechanisms. --- **Note:** If you're asking about a specific plugin, internal API, or a custom protocol specification (e.g., from a particular project or tool), please provide more context or a document reference and I can look into it more precisely.
